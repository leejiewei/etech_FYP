# eTech on Supabase

The MySQL database moved to Postgres on 26 August 2026. All 3,343 rows
from the live MariaDB `etech` database are in project
`asawhkjvturznjitsqfk`, verified row-for-row.

The MySQL scripts in the parent folder are **not** deleted. They are the
history of how the data got built, and 03_seed.sql is still the thing
regenerated from `js/products.js` when the product list changes.

## The files

| File | What it does |
|---|---|
| `01_schema.sql` | 15 tables, 3 enum types, 2 views, the `updated_at` trigger |
| `02_data.sql` | All 3,343 rows, one transaction, parents-first |
| `03_sequences.sql` | Moves identity counters past the loaded ids |
| `04_rls.sql` | RLS on every table — replaces the two MySQL logins |
| `tools/` | The scripts that generated and checked all of the above |

These four run standalone, in order, against any Postgres:

```
psql "$SUPABASE_DB_URL" -f 01_schema.sql
psql "$SUPABASE_DB_URL" -f 02_data.sql
psql "$SUPABASE_DB_URL" -f 03_sequences.sql
psql "$SUPABASE_DB_URL" -f 04_rls.sql
```

`../../supabase/` holds the same content in the layout the Supabase CLI
expects — structure under `migrations/`, data in `seed.sql`. Rebuild it
with `python tools/build_migrations.py` after editing anything here.

**Do not renumber the migration filenames.** Their version numbers match
the rows in the remote project's history. Rename one and Supabase stops
recognising it, then tries to create the tables a second time.

## What changed in the conversion

| MySQL | Postgres | Why |
|---|---|---|
| `AUTO_INCREMENT` | `GENERATED BY DEFAULT AS IDENTITY` | "BY DEFAULT" lets the load insert the original ids; order 2 stays order 2 so `images/<id>.jpg` keeps matching |
| `ENUM('Pending',…)` | `CREATE TYPE … AS ENUM` | Same values, same spelling — `WHERE status = 'Pending'` is untouched |
| `TINYINT(1)` | `SMALLINT` + `CHECK (0,1)` | Not boolean, deliberately: `WHERE is_active = 1` keeps working in the PHP and the Flutter client |
| `TIMESTAMP`, `DATETIME` | `TIMESTAMPTZ` | Every literal carries `+08`, so the Asia/Singapore wall clock survives as the same instant |
| `ON UPDATE CURRENT_TIMESTAMP` | `BEFORE UPDATE` trigger | Postgres has no column-level equivalent |
| `DATE_FORMAT(x,'%Y-%m')` | `to_char(x,'YYYY-MM')` | In `v_monthly_sales` |
| `SUM(e.event_type = 'view')` | `COUNT(*) FILTER (WHERE …)` | A comparison is not 1/0 in Postgres |
| `GRANT` to two DB users | Row Level Security | See below |
| `UNIQUE (name, parent_id)` | `UNIQUE NULLS NOT DISTINCT` | The one tightening: MySQL allowed two root categories with the same name |

### Corrupted text, repaired in transit

336 values in the live MySQL database were mojibake — all 334 product
icons stored as `­ƒÆ╗` instead of 💻, plus `°` and `±` in two
descriptions.

The `.sql` seed files were never wrong. `mysql.exe < 03_seed.sql` on
Windows read those UTF-8 files as cp850, and the cp850 reading is what
got stored. Encoding back to cp850 and reading the result as UTF-8
reverses it exactly, which is what `tools/export_pg.py` does. Anything
plain ASCII, or that cp850 cannot represent, is left alone.

**The MySQL database still has the mojibake.** Only the Postgres copy is
clean. Re-importing the old seed files the same way would reproduce it —
pass `--default-character-set=utf8mb4` and redirect through a UTF-8-aware
shell if you ever need to.

### Security: what replaced the two logins

MySQL had `etech_client` (no `cost_price`, no writes) and `etech_admin`
(everything). Supabase has no equivalent, because the client is now
whoever holds the anon key, talking to PostgREST directly.

`04_rls.sql` enables RLS on all 15 tables and defines **no policies**, so
the anon key reads nothing and writes nothing. Verified: `SELECT` returns
`[]`, `POST` returns 401. The PHP app is unaffected — it connects over
the Postgres connection string as the table owner, and an owner is not
subject to RLS.

Both views are `security_invoker = on`. Without that a view runs with its
definer's rights and `v_product_velocity` would have leaked the whole
catalogue past the policies.

If the Flutter client is ever pointed straight at Supabase instead of at
`web/api/*.php`, the commented block at the bottom of `04_rls.sql` is the
starting point — it draws the same line `etech_client` did, including the
column-level `REVOKE` on `cost_price`.

> During the load itself the tables were briefly writable by the anon key,
> because Supabase's default grants apply until RLS is switched on. That
> window is what made the fast import possible, and `04_rls.sql` closed
> it. Nothing else was exposed.

## The tools

Run from this directory. All of them read the live MariaDB `etech`
database, so XAMPP's MySQL has to be running.

```
python tools/export_pg.py ../supabase/02_data.sql      # regenerate the data file
python tools/load_via_rest.py                          # load over PostgREST
python tools/verify.py out.sql expected.json           # fingerprint both sides
python tools/build_migrations.py                       # rebuild ../../supabase/
```

`load_via_rest.py` needs the endpoint in the environment, so no key is
committed here:

```
set SUPABASE_URL=https://asawhkjvturznjitsqfk.supabase.co
set SUPABASE_ANON_KEY=<publishable key>
```

It only works while RLS is off, i.e. between `01_schema.sql` and
`04_rls.sql`. After that it gets 401, which is the point.

### How the transfer was checked

`verify.py` flattens every row to text, joins it, and hashes the table —
then emits the Postgres query that does the same thing on the other side.
Comparing 15 hashes proves more than comparing 15 row counts, which would
miss a value that arrived wrong.

Both sides have to spell values identically for that to mean anything, so
NULL becomes `\N` (an empty string is a real value and must not collide),
decimals are compared as text rather than floats, and timestamps are
rendered as Asia/Singapore wall clock on both sides — Postgres stores UTC
now, so the raw text would differ by eight hours on every row.

All 15 matched.

## Pointing the website and the app at Supabase

Done on 26 August 2026. `web/api/db.php` and `web/admin/inc/db.php` are
now PDO with the `pgsql` driver; nothing above them changed name or
signature, so every page still calls `query()`, `fetchAll()`, `fetchOne()`
and `fetchValue()` as before.

Nothing connects to Supabase except those two files. The browser and the
Flutter app both call the PHP API, which is why the database password can
stay on the server:

```
Flutter app  ─┐
              ├─>  PHP API (web/api/)  ─>  Supabase (Postgres)
Web browser  ─┘

Admin panel (web/admin/)  ─────────────>  Supabase (Postgres)
```

### Before it will run

1. **Fill in the connection string.** Supabase dashboard → Connect →
   **Session pooler** (port 5432, user `postgres.<project-ref>`), and paste
   it into `SUPABASE_DB_URL` in `config/etech_config.php`. Setting an
   environment variable of the same name overrides the file, which is the
   better place for the password. Do not use the transaction pooler
   (6543) — it cannot run the prepared statements this code depends on.
2. **Switch on the driver.** In `php.ini`, uncomment `extension=pdo_pgsql`
   (the DLL already ships with XAMPP), then restart Apache. MySQL no
   longer needs to be running at all.

### What had to change in the SQL

| MySQL | Postgres | Where |
|---|---|---|
| `mysqli` + `bind_param` types | PDO, values bound positionally | both `db.php` files |
| `db()->insert_id` | `INSERT … RETURNING <id>` | `api/auth.php`, `api/orders.php` |
| `ON DUPLICATE KEY UPDATE` | `ON CONFLICT (…) DO UPDATE` | `api/cart.php` |
| `begin_transaction/commit/rollback` | `dbBegin()/dbCommit()/dbRollback()` | `api/orders.php`, `admin/orders.php` |
| `IFNULL()` | `COALESCE()` | dashboard, reports, forecast, velocity |
| `SUM(col = 'x')` | `COUNT(*) FILTER (WHERE col = 'x')` | `admin/velocity.php`, `admin/alerts.php` |
| `DATE_FORMAT(d,'%Y-%m')` | `to_char(d,'YYYY-MM')` | `admin/reports.php`, `admin/forecast.php` |
| `DATE_SUB/DATE_ADD(NOW(), INTERVAL n UNIT)` | `NOW() ± INTERVAL 'n unit'` | alerts, velocity, reports |
| `LIKE` (case-insensitive in MySQL) | `ILIKE` | `admin/products.php` search |

Two smaller things the clients would otherwise have noticed:

- **Dates.** Postgres returns `2026-08-26 11:07:00+08` where MySQL returned
  `2026-08-26 11:07:00`. The connection asks for `Asia/Kuala_Lumpur`, so the
  clock is already right, and `tidyTimestamps()` in both `db.php` files
  trims the offset — the JSON reaching the browser and the Flutter app is
  byte-for-byte what it was.
- **PHP's own clock** is pinned to the same zone in `config/etech_config.php`,
  so "the last 30 days" means the same thing in PHP as it does in Postgres.
